# Security status: engineering alpha, not public launch

## Implemented and tested locally

Verified cookie sessions through Better Auth; strict command schemas; server-authoritative roles and authors; private-space and nested-resource filtering; tenant foreign keys; transaction-local RLS context; PostgreSQL rate counters; request body cap; Origin checks on cookie-authenticated mutations; safe HTTPS links; React text escaping; one-time rewards; transaction rollback; idempotency receipts; tenant/actor cache boundaries; non-owner production credential check; explicit live/demo separation.

Database tests run SQL in PGlite, including explicit restricted-role RLS tests. PGlite is an embedded Postgres runtime, not the customer's Neon instance. Its concurrency scheduling does not establish high-load Neon performance. Staging tests against a real pooled Postgres connection remain required.

The storage boundary is tested with explicit stand-in providers and the real Google SDK's offline signing; no real bucket upload, IAM or CORS configuration has been verified. Alpha 09 exposes private lesson files to members (LESSON_RESOURCES.md): uploads are track-scoped and author-only, completion checks size, type and the file signature from the first stored bytes, and the verified object generation is pinned for every later read. Downloads are two-minute signed URLs with attachment disposition, gated by current lesson, space, role and tenant access, with a restrictive RLS policy as defence in depth. Member-private uploads keep their owner-only API. There is still no malware scanning or deep Office-file inspection, and nothing is rendered inline.

Alpha 10 knowledge checks (ASSESSMENTS.md) keep answer keys on the server: lessons reach members without correct options, accepted answers or explanations, and a learner's own attempts show them only under the author's reveal rule. Scoring happens only on the server; answers to a changed check are refused by fingerprint. `quiz_attempts` has forced RLS (own rows for members, the tenant's rows for active owners/admins), inserts must be the caller's own, unreviewed and at version 1, a review must be by an active owner/admin who is not the learner and can happen only once (unreviewed before, reviewed at version 2 after), the runtime role cannot delete attempts and may update only review columns. Attempts are retained; an erasure procedure for a learner's answers is not yet built. (Alpha 14 added the operator erasure; Alpha 15 lets a person's own attempts go with their account, and no one else's.)

Alpha 11 cover images (COVERS.md) reuse the verified upload pipeline: an intent bound to exactly one track or project, a five-minute signed POST for an exact key, type and size, and completion that checks the signature and the declared dimensions (16 to 4,096 pixels) from the first 64 KB of the pinned generation, deleting refused objects. The browser redraws every picture before upload, so camera metadata such as location never reaches storage. Bytes are served only through a same-origin route that checks tenant, space access and publication of the record displaying the cover on every request, with `private` caching, `nosniff`, inline disposition and a `default-src 'none'; sandbox` policy, so a stored file cannot run as a document. A restrictive RLS policy limits members to cover uploads a visible published track or project displays. A browser that already loaded a cover can show it from its private cache for up to an hour after access ends, and removed pictures stay in private storage until a later cover upload prunes them.

Alpha 12 track instructors (INSTRUCTORS.md) are explicit grants: `track_instructors` has forced RLS, only an active owner or administrator inserts a grant in their own name or deletes one, and the runtime role cannot update grants. Instructors are admitted per track by new permissive policies on drafts, revisions and attempts and by the recreated restrictive lesson file policy; every clause requires a grant for the row's own track and an active membership, so suspension ends access at once. Attempt review keeps its once-only shape and never allows reviewing one's own attempt. The connected instructor check runs the live API under the restricted runtime role with forced RLS.

Alpha 13 cover library (COVERS.md) adds `cover_library` with forced RLS: read within the tenant, inserted only by an active owner or administrator in their own name, deleted only by them, and never updated by the runtime role. A restrictive `cover_library_read` policy keeps a library upload with its active uploader and active owners and administrators until it is listed. Library pictures use the verified upload pipeline and are served by the same hardened route shape as covers, at `/cover-library/:itemId`, to active members only. There is no stock photo search, third-party key or remote image address. Removing an unused picture deletes its stored file at once; a picture in use cannot be removed. The connected cover check now runs the live API under the restricted runtime role with forced RLS.

Alpha 14 learner records (LEARNER_RECORDS.md) let a member download only their own record, read inside their own tenant transaction under the restricted runtime role and sent as a `no-store` attachment; titles, names and answer keys follow the member's own view. Erasure is an operator procedure on the migration connection, authorised by an active owner and run inside that owner's tenant transaction, dry run by default, refusing partial erasure and auditing counts only. Migration 0014 adds one delete policy on attempts that admits only the member named in `app.erasure_subject` when the acting user is an active owner, so forced row security stays in force for a migration role without BYPASSRLS; the runtime role has no DELETE on attempts. Unused cover files are deleted before their records. Account deletion and identity scrubbing are not implemented. (Alpha 15 added both; see below.)

Alpha 15 account deletion (ACCOUNTS.md) lets only the signed-in person delete their own account: a same-origin JSON request, rate limited to five attempts in fifteen minutes, with the current password checked by Better Auth and the typed phrase "delete my account". Everything happens in one transaction under the restricted runtime role with forced RLS. The transaction is marked with `app.account_deletion` set to the acting user, and migration 0015's policies admit only that user's own rows while the mark is present: all their memberships (any status), their instructor grants and their knowledge-check attempts. The runtime role now holds DELETE on `quiz_attempts`, bounded by a restrictive policy to exactly that case, so it can never delete another member's attempts or use the owner-authorised erasure policy from 0014. A shortfall between the planned and admitted deletes rolls everything back. Owners are refused. Each membership becomes the same scrubbed "Former member" record (status `left`), shared work stays attributed to it, and personal records, private files (objects removed after commit), invitations to the address, queued mail to it (sealed payloads opened only to compare recipients), reset tokens, sessions, the password hash and the account go; the session cookie is cleared. The audit entry holds counts only. A former member cannot sign in, receive messages, notices, points, roles or grants, or be restored. After applying 0015, re-run `npm run db:grant-runtime` so the runtime grant matches the code.

Alpha 21 two-step sign-in (ACCOUNTS.md, decisions/021-two-step-sign-in.md) uses Better Auth's own two-factor plugin: authenticator-app codes (RFC 6238) and ten single-use backup codes, both encrypted with the session secret in `auth_two_factor` (migration 0021, explicitly granted to the runtime role, removed with the account, never part of a workspace or session payload). Turning it on needs the password and a correct code; turning it off and new backup codes need the password. A password sign-in on an account with two-step sign-in creates no session until the second step succeeds; Better Auth limits each challenge to five attempts, locks the account for 15 minutes after ten consecutive failures and rate limits two-step requests per address. `ADMIN_TWO_FACTOR` (`required` by default in production, validated at start-up) makes owner and administrator authority depend on it: workspace commands that succeed only because of the role, and the owner and administrator routes, return 403 `TWO_FACTOR_REQUIRED` for an account without it, while reads and member or moderator actions continue. Not yet: recovery without backup codes, passkeys, a used-code record within the 30-second window, and hosted verification.

Alpha 26 email confirmation and change (ACCOUNTS.md, decisions/026-email-confirmation-and-change.md) use Better Auth's own flows with links queued in the encrypted outbox. A confirmation link works once for 24 hours and goes only to the address it confirms; accepting an invitation confirms the invited address. `EMAIL_VERIFICATION` (`required` by default in production, validated at start-up, applied only where mail can be sent) refuses a session to an unconfirmed address and queues a fresh link. Changing the address needs the current password at `POST /api/account/email` (five attempts in fifteen minutes); Better Auth's own `/api/auth/change-email` is closed. The address changes only when the link sent to the new address is opened, the current address is told with the new one masked, and a taken address gets the same answer and no mail. Opening a change link while signed out creates a session without the second step, as Better Auth does.

## Before a public or paid launch

- Invitation expiry/revocation and password recovery/session revocation are implemented and locally tested. Still verify actual provider delivery, trusted proxy/IP handling and hosted cookies. Email confirmation and password-checked address change are implemented (Alpha 26); set `EMAIL_VERIFICATION=required` with a verified sender on the hosted deployment. Privileged-account two-step sign-in is implemented (Alpha 21); verify it on the hosted deployment and set `ADMIN_TWO_FACTOR=required` there.
- Verify reverse-proxy origin/client-IP trust, abuse controls and rate-limit behaviour. Never trust arbitrary forwarding headers.
- Run independent authorisation/security review, live Neon tenant-isolation tests and a real restore rehearsal. Add monitoring and incident procedures.
- Implement retention/export/deletion flows, policy notices and documented handling of reports. Do not claim regulatory compliance from a technical prototype.
- Add bounded/paginated read endpoints, worker delivery with retries and appropriate indexes before scale. Outbox, receipt, rate-table, session and mail retention is built (RETENTION.md) but must be scheduled.
- Connect real storage with private IAM and exact-origin CORS, verify signed uploads and downloads against the real bucket, add malware/content scanning and an orphaned-object sweep, and define an operator procedure for removing published files that contain personal data. Generation pinning and signature checks are implemented; they are not a substitute for scanning.
- Review the complete transitive dependency/SBOM and known vulnerabilities; CI must enforce these gates. Build success is not a vulnerability audit.
- Verify Vercel function routing, cookie security, preview isolation, bundle size, operational cost caps and production environment settings.

## Secret handling

Do not commit `.env`, database URLs, authentication secrets, service-account JSON, bootstrap passwords or signed URLs. Only `VITE_DATA_MODE` is a public frontend setting. The server fails closed on missing configuration. Never configure an administrative database credential as the production application role.

Default demo data is fictional and browser-local. The demo contains switchable roles deliberately for evaluation; no production API recognises these identities. Do not use the preview for confidential information.


## Alpha 02 purpose and evidence boundaries

Member goals are private by default and filtered even from ordinary community administrators. Member sharing is an explicit visibility choice. The application does not expose goal content through search or automatically place it in activity/outbox payloads. This is not end-to-end encryption from the database operator.

Paths and milestones inherit access restrictions from their linked lesson, mission and project resources. Publishing validates the full path audience. Recognised contributions, verified outcomes and community outputs are filtered together with their source resources; a public-looking page is not permission to expose private work. Output publication is currently a member-visible community archive.

Review transitions are server-authorised. A project owner or community administrator can review another member's contribution; an administrator verifies another member's outcome. No reviewer may approve their own contribution or outcome. Feedback, reviewer identity and timestamps are recorded. An outcome requires exactly one eligible owned, reviewed source; membership or a plain update does not count as proof. A goal completes only from a completed linked path or an explicitly selected verified outcome owned by that member and linked to that purpose.

The new eight tables have tenant foreign keys, RLS and explicit runtime-role grants. `db:grant-runtime` refuses an elevated role, table-owning role or a role with membership inheritance; it does not grant schema ownership or access to migration checksums. Per-user privacy is domain-level in addition to tenant RLS, not a claim that tenant RLS by itself knows which member is accessing each row.

Community verification is not accreditation or independent validation of a real-world claim. Preserve source-review attribution. Revocation, appeal histories, multi-contributor credits and consented cross-community discovery need further design before introduction. Do not infer sensitive capability or publish personal goals to power later matching or AI.


## Alpha 03 privacy and account boundaries

Invitation tokens are hashed; reset handling uses Better Auth. Both kinds of outgoing links are stored only in encrypted mail payloads until delivery, then cleared from sent jobs. Invitation creation returns its personal link once to an authorised inviter. Do not log that response. Verify email sender ownership before launch, and schedule the retention job (RETENTION.md), which clears finished mail records after 90 days and undelivered mail contents after 30.

Conversations and messages are participant scoped at both API and forced RLS layers. Group conversations (Alpha 24, decision 024) use the same participant list; someone added to a group later is kept from earlier messages by a restrictive select policy as well as the API, and leaving relies on a one-transaction mark (`app.leaving_conversation`) set only after the API confirms they are in the group. Moderators receive only a member-selected report excerpt, not inbox access. Message text is plaintext to the server/database operator and is NOT end-to-end encrypted. Browser-demo localStorage is untrusted fictional state, not a secure store for real conversations.

Suspension preserves work and denies new requests. The transaction boundary rechecks active membership after lock acquisition. New roles cannot be self-granted. Private-space administrative access does not give application admins access to private goals or third-party inboxes.

Blocking, input limits, sender-authority checks, throttling and duplicate-send keys are implemented. Export/deletion of message history, sender-bounce webhooks, independent penetration testing and a staffed abuse escalation process remain unbuilt or unverified.


## Alpha 04 release and operations boundary

Operational status is owner-only and never exposes mailbox content, personal goals, recipients or secrets. Database-owner, public-object-owning, schema-creating and role-assuming connections are now rejected by the runtime safety check, alongside superusers and BYPASSRLS. Canonical production HTTPS, independent email encryption, secret-prefixed Vite variables, weak configured worker secrets and migration/bootstrap runtime credentials have explicit guards.

The publication helper verifies the supplied manifest and refuses differing target files before copying, except the known original README placeholder. It does not erase files, force-push or merge main. Hash verification detects changes relative to the supplied manifest, not authenticity or malicious upstream code. The Git bundle is an offline release transport and must be reconciled against current remote work before integration. No code should bypass provider safety checks or browser navigation restrictions to make a deployment claim.
