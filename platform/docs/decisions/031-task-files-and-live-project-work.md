# Decision 031: task files reuse the lesson-file pipeline, and live project work is a cheap change check

Status: implemented in Alpha A3 (placeholder number, renumbered at merge), verified locally; not deployed. Date: 3 October 2026.

## Problem

Project workboards (Alpha 05) had no way to keep a draft, a reference or a picture with the task it belongs to, and nothing on screen changed until someone pressed Refresh or the 30-second workspace reload came round. Two people editing one task were already protected by a version check, but the second person only saw "This task changed. Refresh the workspace", lost sight of what they had typed, and was never told who had changed it. ROADMAP.md listed both as the Alpha 05 limitation.

The application deploys as serverless Hono functions on Vercel. No websocket server, pub/sub service or queue is provisioned, and this slice may not provision one.

## Decision

### Task files

- **One upload pipeline.** A task file is an `upload_intents` row with `purpose = 'task_file'` and a `task_id`, started through the existing `POST /uploads` (`{purpose:'task_file', taskId, name, contentType, sizeBytes}`), uploaded straight to the private bucket with the same five-minute signed POST policy for an exact key, type and size, and completed through the existing `POST /uploads/:id/complete`. Completion takes the lesson-file branch: stored size and type, then the first kilobyte read at the measured generation and checked against the file signature; a mismatch is refused and its object deleted. The key is `organisations/{organisation}/task-files/{project}/{uuid}.{ext}`, under the project rather than the uploader.
- **Same types and size as lesson files.** PDF, Word, PowerPoint, Excel, JPEG, PNG or WebP, up to 10 MB each. Twelve files per task (as per lesson), 200 verified files per project, five unfinished uploads per person. An uploader's own refused or hour-old unfinished uploads are pruned when they start another.
- **Files belong to the task, not to comments.** Notes stay plain text. A file on the task is visible wherever the task is, and a note can refer to it by name; attaching files to individual notes would add a second scope with its own removal and moderation rules for little gain.
- **Who.** Anyone who can work on the project now (`canWorkOnProject`: an active member of the community who is on the project team, leads it or administers the community, and who can open the project's space) can attach a file to a task that is not archived, see its files and download them. The uploader or the project lead (or an owner or administrator) removes a file. When `ADMIN_TWO_FACTOR` is required, an owner or administrator without two-step sign-in is refused `TWO_FACTOR_REQUIRED` when attaching to a task whose team they are not on, or when removing a file only their role lets them remove; team members and leads are never asked.
- **Downloads.** `GET /api/organisations/:slug/tasks/:taskId/files/:fileId/download` runs one domain gate, `resolveTaskFileDownload`, against current state and returns a two-minute signed link pinned to the verified generation, with attachment disposition and the recorded type, exactly as lesson files do. A suspended person, someone removed from the team or the private space, another community and an anonymous visitor all get 401 or 404 at once. The member-private download route still refuses every non-member upload.
- **Removal.** `task.file.remove` is a workspace command. The record goes in the change; the stored object is deleted straight after the change commits (`releasedTaskFileKeys`, beside the cover rule from Alpha 17). Removing works on archived tasks too, so a mistake can always be taken back.
- **Defence in depth.** Migration 0031 adds four restrictive policies on `upload_intents`, each a no-op for other purposes. Reading a task file needs a verified file on a task the reader's own `project_tasks` policy admits (so team, space and active membership are checked by PostgreSQL), or the uploader's own unfinished upload while they are active, or the uploader's own rows while they delete their account, or an active owner or administrator. Inserting needs the uploader's own name and a task the team policy admits that is not archived. Only the uploader updates one. Deleting needs the uploader, the project's lead or an active owner or administrator. Checks keep every task file bound to exactly one existing task in the same community and require a generation once ready. No table was added, so the existing explicit grant on `upload_intents` covers it.
- **Account deletion.** A deleted person's files on shared tasks are shared work and stay, shown as from a Former member; the project lead or an administrator can remove them. Their uploads that never became files (pending or refused) are theirs alone and go, records and stored objects, counted as `taskFileUploads` in the summary. The operator command `npm run db:prune-covers` now also lists and clears task uploads that never became files (refused, or unfinished after an hour); attached files are never pruned.
- **Demo.** The same domain functions run in the browser and the bytes stay in this browser (IndexedDB, or memory), as lesson files do.

### Where a scan verdict would gate a download

Alpha 23 (upload scanning, built in parallel) adds scanning to the shared upload path. Task files use that path unchanged, so a scan applies to them as soon as it lands. Three places would then read the verdict: completion in `apps/api/src/app.ts` (the shared `lesson_resource` / `task_file` branch, where `observed` is assembled before `completeTaskFileUpload`), `resolveTaskFileDownload` in `packages/domain/src/task-files.ts` (beside `upload.status !== 'ready'`, so an unscanned or infected file is never released), and `visibleTaskFiles` in the same file (so the team does not see a Download button for a file that would be refused). The read policy `task_file_read` could add the same condition in a later migration.

### Live project work

- **A change check, not a connection.** While a workboard (and any task opened from it) is on screen, the browser asks `GET /api/organisations/:slug/projects/:projectId/changes` every five seconds while the tab is visible. The answer is an opaque 16-character fingerprint of everything the board and an open task show (the project heading, the team, every task's version and state, the notes, the verified files and the proof linked to tasks), with a matching `ETag`; the browser sends `If-None-Match` and an unchanged board costs an empty `304`. The server reads only the collections that decide access and draw the board, inside the person's own tenant transaction. Only someone who can work on the project may ask; everyone else gets the same 404 as for a missing project.
- **Quiet.** When the fingerprint moves, the board's workspace is fetched again and, if that brought different work onto the screen, a small status line reads "Updated just now" (then "Updated at 14:02"). The person's own saves are already on screen, so they never read as someone else's update. Hidden tabs stop asking and ask again when shown; errors back off, doubling up to a minute, and the line reads "Reconnecting…".
- **Replaceable.** The page uses one hook, `useProjectChanges`, over one transport, `watchProjectChanges(slug, user, project, onChange)`. A server-sent events stream or a hosted pub/sub channel can replace the poll inside that function without touching the page. In the demo, the transport reads the other tab's saved state from browser storage.
- **Optimistic concurrency, made visible.** Every task change already carries `expectedVersion`; migration 0031 adds `project_tasks.updated_by`, set on every change (NULL for older rows and for tasks released by an account deletion). The task editor saves against the version it loaded. If live updates bring a newer version, or the save is refused with `STALE_TASK`, the editor shows "Idris Cole changed this task while you were editing at 14:02", keeps the person's typing in the form, disables Save and offers **Load the latest version** or **Keep my edits** (which saves over the newer version only when chosen). Claim, start, release, archive and proof buttons reload the task after a refused stale action. The refusal message itself now says that someone else changed the task.
- **No presence.** Showing who else has a task open would turn reading into recorded activity: every poll would become a database write, and viewing is exactly the kind of private behaviour the doctrine keeps out of shared view. It is left out; the decision can be revisited if a pilot asks for it, as opt-in and team-only.

## Alternatives considered

- **A `task_files` attachment table.** A separate row per attachment would duplicate what an upload intent already records (name, uploader, type, size, generation) and add a second deletion path. The intent with a task scope is the attachment.
- **Websockets, SSE or a pub/sub provider now.** Vercel functions are short-lived, and every hosted channel is new infrastructure, a new secret and a new failure mode the brief rules out. A five-second fingerprint check is a few hundred bytes per minute per open board.
- **Polling the whole workspace faster.** The snapshot reads every collection in the community; the change check reads nine and answers 304 when nothing moved.
- **Last write wins with a merge.** Task fields are short and few; silently merging a title or a brief would hide one person's words. Showing the conflict and letting the person choose is honest and cheap.

## Consequences

Teams keep the files a task needs beside its brief, criteria and notes, released only to the people who can work on it at that moment. Boards and open tasks update within seconds without new infrastructure, and two people editing one task can no longer overwrite each other without knowing. Each open board adds about 12 small requests a minute, and each one passes the existing per-member rate limit (240 reads a minute) and its counter write. Real Google Cloud Storage signing, CORS and deletion remain unverified against a real bucket, as for every upload. There is no virus scanning until Alpha 23 lands, no preview of file contents, no presence and no live updates outside project workboards.
